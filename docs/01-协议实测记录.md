我们的解析器不是手写偏移，而是按官方字段顺序自动累加。用它算出的 **Horizon 布局**是：


这与两个独立的 FH6 项目里硬编码的数字**完全一致**。说明"字段顺序 + 累加"这套方法是可靠的，因此同一方法算出的 FM8（Dash@232 / speed@244 / gear@307）可信度较高——但仍需实测反证。

## 二、档位语义（关键）

### 已确认

| 事实 | 来源 |
|---|---|
| **FM8 的这辆车没有可选的空挡**：R 挡与 1 挡之间不能通过"升/降挡"键进入 N | 用户实车操作（2026-11-04） |

> 注意区分两件事：**"没有 N 挡可选"** ≠ **"遥测里不会出现 0"**。
> 前者说的是操作层面（你无法挂进去），后者说的是数据层面（可能作为发车初始值或换挡中间值出现）。
> 下面的设计全部围绕这个区分展开。

### 由此推出的结论

1. **`gear > 10` 不是 FM8 的"换挡中"标志。**
   参考项目用 `is_shifting = gear > 10`，那是 Horizon 的语义（11 = N）。FM8 既然没有 N 挡，这个判断在 FM8 上永远不会成立——照搬会得到一个"永远认为没在换挡"的解析器。

2. **但 `gear == 0` 变得更危险，而不是更安全。**
   没有 N 挡不代表遥测里不会出现 0。已知会出现的场景：
   - 倒挡（正常）
   - 发车格/加载完成瞬间（另一个项目的注释明确记录："at a race start the game reports gear 0"）
   - 换挡动画的个别帧（待测）

   所以 **不能只凭 `gear == 0` 判定"在倒车"**。

3. **判定前进/后退必须用车速方向，不能用档位。**
   Sled 段的速度是车体坐标：X = 右，Y = 上，**Z = 前**。
   因此 `VelocityZ < 0` 才是"真的在后退"。判据应写成：

   ```
   在倒车 ⟺ velocity_z < -1.5 m/s 且 |速度| > 2 m/s
   ```

   只看档位会把"发车瞬间的 0"误判成倒挡，导致程序在起跑时完全被动（这正是另一个项目的处理方式：起跑低于 10 km/h 一律不发指令）。

### 待测

| 问题 | 怎么测 | 为什么重要 |
|---|---|---|
| 倒挡时 `Gear` 到底是几 | 停稳挂 R，看读数 | 确认 0 |
| 1 挡时是 1 吗 | 停稳挂 1 挡 | 确认从 0 跳到 1 |
| 换挡瞬间 `Gear` 会不会短暂变成 0 或别的值 | 连升三挡，看"最近换挡"日志有没有 `2 → 0 → 3` 这种 | 决定"换挡中"怎么判定 |
| 最高挡是几 | 跑到红线看最大读数 | 决定档位合法区间，不能假设 10 |

这段数据是**决定性证据**，全部结论基于它：

```
记录 4265 帧 / 50.5s / 84.5 帧每秒；唯一时间戳 3212，重复 1053（24.7%）

最高转速 8271 / 名义红线 9000（92%）
```

#### 换挡过程完整还原（15 次换挡）

每一次换挡，档位序列都是 `X → 11 → X±1`，没有例外：

| 类型 | 次数 | 11 持续时长 | 车速范围 |
|---|---|---|---|
| 升挡 | 8 | **70–71 ms**（极其稳定） | 115–220 km/h |
| 降挡 | 7 | 95–153 ms | 47–228 km/h |

- **`Gear = 11` 就是"正在换挡"**，即变速箱处于两挡之间的空挡位。用户直觉是对的（"11 是空挡"），只是它不是可挂入的空挡，而是换挡过程的中间态。
- **换挡期间 `Clutch` 恒为 0** —— 说明这个字段读的是离合器踏板位置，游戏自动补油/自动离合时不会反映出来。**不能用离合判断换挡，必须用 `Gear == 11`。**
  - 补充（用户说明 2026-11-04）：该车用的是「手动」而非「手动 + 离合」，所以本来就没有离合操作。若改用「手动 + 离合」或踩离合踏板，这个字段应当会有值。**阶段 5 做离合辅助时再单独验证。**
- 升挡 70ms、降挡 100–150ms，**这直接决定了换挡冷却时间的下限**：冷却必须 > 160ms，否则会在换挡过程中再发指令。

#### 关于 `Gear = 0` 的最终结论

本次记录里 `0` 只出现在**最开始 0.01s 和最后 46.56s**，且 `EngineMaxRpm = 0`、`is_race_on = 0`。

用户补充说明：**截图时会切出游戏，游戏自动暂停并进入菜单**。这解释了之前的 200 个"有效" gear-0 帧——它们是**暂停菜单**，不是行驶状态（暂停时发动机仍在怠速，所以 `EngineMaxRpm` 仍有效）。

因此：

> `Gear = 0` = **菜单 / 暂停 / 未入挡 / （可能）倒挡**。
> 它**不是**"倒车"的可靠标志。判定倒车必须用 `velocity_z < 0`。

#### 顺带确认的两条

- **名义红线不可信**：这台车名义 9000，实际只跑到 8271（92%），而且用户是主动在 ~85% 换挡的。真断油点还需要专门拉一次红线才能测到。
- **重复帧不影响正确性，但影响节奏**：24.7% 的重复包如果不去重，同一帧会被决策两次。

### 由此确定的四条结论

#### ① 发送频率 = 渲染帧率，不是固定 60 Hz ✅

84.4 包/秒 vs 85 FPS，误差在噪声范围内。**官方文档的"60 packets per second"在 PC 上不成立。**

设计影响：
- 主循环**不能**假设"每 16.7ms 一帧"
- 帧率变化时数据量会变，缓冲区要留余量
- 高帧率（144/165）下包量接近翻倍，接收线程要扛得住

#### ② 约 25% 的包是"同一帧的重复包" ✅

2085 个包里 517 个与前一包时间戳完全相同，唯一帧只有 1568 个。
配合"最小间隔 2.53ms"，说明包是成簇到达的。

设计影响：**决策前必须按 `TimestampMS` 去重**。否则同一份数据会触发两次判断，
虽然不会致命（条件相同结果相同），但会让"冷却时间"被重复消耗，表现为换挡变慢。

#### ③ `Gear = 0` 不是"倒挡专用值"，而是"非前进挡" ✅

这次 200 个有效帧里，`Gear = 0` 的**平均车速 0.0、最高车速 0.0、转速 785（怠速）**。
也就是说：车停着、发动机转着，档位读 0。

结合第一次数据（大量 0 与"发动机未启动"重叠），可以确定：

> `0` = 倒挡 **或** 空挡 **或** 静止未入挡。三者无法从档位数字区分。

**判据必须叠加物理量**：

```
真的在倒车 ⟺ velocity_z < -1.5 m/s 且 |speed| > 2 m/s
```

#### ④ `Gear = 11` 是"换挡过渡帧"，不是空挡 ✅（强证据）

- 54 帧，**平均车速 89.7 km/h**，最高 167.9 km/h，平均转速 4318 —— 明显是行驶中
- 它的**最高车速 167.9 与 3 挡的最高车速 167.8 几乎完全相等** —— 说明它出现在 3→4 的换挡点上
- 平均车速远低于 3/4 挡均值（143.6 / 144.9）—— 说明低速的降挡过程中也出现过

所以 `11` 是变速箱在"两挡之间"时的占位值。

> 这解释了为什么用户觉得"没有空挡"：操作上确实挂不进去，但换挡执行的瞬间，
> 游戏会把档位置为一个"非有效挡"，值就是 11。地平线把 11 解释成 N，本质相同。

**因此 `is_shifting` 在 FM8 上应该判 `gear == 11`，而不是 `gear > 10` 之类的范围判断。**
但仍需"跳变序列"证据确认它总是夹在两个相邻挡之间（探针已加该统计）。

#### ⑤ 必须过滤"发动机未启动"帧 ✅

441 帧 `EngineMaxRpm = 0`（菜单/加载/暂停）。这些帧的所有数值都不可信
（档位是 0、车速是 0、转速是 0），**绝不能进入决策**。

## 四、已知的坑（写在代码注释里，防止以后忘）

1. **不要用 `gear > 10` 判换挡** —— 范围判断会误伤。FM8 的换挡占位值是精确的 `11`（实测：54 帧，全部出现在行驶中）。
2. **不要用 `gear == 0` 判倒车** —— 它同时代表倒挡、空挡、静止未入挡（实测：200 个有效帧全部 0 km/h）。必须叠加 `velocity_z < 0`。
3. **不要假设最高 10 挡** —— FM8 有 6/7/8 速车，上限要可配或从学习推断。
4. **不要用 FH 的 Dash 偏移** —— 整体差 12 字节，而且不会报错，只会输出垃圾。
5. **不要设 `SO_REUSEADDR`** —— Windows 上会让第二个实例静默抢端口。
6. **不要按"帧率 = 60"做设计** —— 实测 84.4 包/秒（85 FPS）。高帧率下还会更高。
7. **不要同一份数据算两次** —— 约 25% 的包与前一包时间戳相同，必须去重。
8. **不要用"发动机未启动"的帧做任何判断** —— 菜单里游戏照样发包，数据全零。
