## 0. 一页结论

| 结论 | 说明 |
|---|---|
| 参考项目**不能直接改**成 FM8 版 | 它的遥测解析是**硬编码字节偏移**，且偏移是按 Horizon 布局写的。FM8 的 Dash 区整体**前移 12 字节**，直接跑不会报错，只会输出一串"看起来合理但是错"的数据 |
| 值得复用的是**算法思想与工程结构** | 齿比学习、功率曲线拟合、断油转速检测、防抖动、换挡确认与退避——这些是它迭代到 13.2.8 版、18 个 release 沉淀下来的经验，价值最高 |
| 代码层面建议**独立实现** | 该项目是 **AGPL-3.0**，直接抄代码会把你的项目整体"传染"成 AGPL。独立实现算法（思想不受版权保护）则不受限 |
| 输入方案：vJoy 优先，键盘保底 | 第二个项目默认 vJoy、键盘写了 4 种注入方式，说明键盘会漏；FM8 能否绑 vJoy 按钮仍需阶段 3 实测 |
| 首版应砍功能 | 参考项目的 4 模式 + 5 类特性开关，是一个大版本接一个大版本堆出来的。FM8 首版建议只做 `SPORT` + `RACE` + `MANUAL`（只提示不换挡） |

## 1. 参考项目结构说明

| 项目 | 数值 |

| Python 核心代码 | 53 个文件 / 7,640 行（`virtual_tcu/`） |
| 测试代码 | 23 个文件 / 3,703 行（22 个测试模块 + `conftest.py`） |
| 最大单文件 | `virtual_tcu/logic/tcu.py` — 2,296 行，单个类 `TCULogic` 约 60 个实例字段 |

### 1.2 后端分层（这块设计是对的，值得学）

```
virtual_tcu/
├─ config/        constants.py（默认参数表）/ store.py（JSON 读写 + 类型校验）
├─ telemetry/     receiver.py（UDP 线程）  parser.py（定长偏移解析）
│                 model.py（Telemetry dataclass + 派生属性）
│                 logger.py（二进制录制 .bin.gz）  udp_hub.py（转发给第三方仪表）
│                 car_key.py（车辆指纹）  fusion_logger.py（快照）
├─ learning/      gear_ratio.py（齿比）  power_curve.py（功率曲线）
│                 rev_limiter.py（断油转速）  drive_style.py（驾驶风格指数）
├─ detectors/     airtime.py（腾空）  yaw_transient.py（横摆瞬态）  reverse_hold.py（倒挡）
├─ logic/         tcu.py（状态机 + 5 种模式）  ← 全部决策集中在这一个文件

├─ state/         shift_history.py  session_stats.py  watchdog.py  graph_buffer.py

├─ web/           server.py（aiohttp + WebSocket → 前端仪表盘）
└─ app.py         组装：配置 → 输出后端 → TCU → UDP 接收 → Web 服务
```

依赖方向基本是单向的：`config → telemetry → learning → logic → input`，`app.py` 负责注入。这个骨架可以直接借鉴。

### 1.3 数据流

```
游戏 ──UDP 60Hz──> TelemetryReceiver(线程) ──解析──> Telemetry
                                            │
                                            └─> TCULogic.process()  ← 在**接收线程里同步执行**
                                                    │
                                                    ├─> OutputInterface.shift_to()  ──> 键盘 / vJoy
                                                    ├─> ShiftHistory / SessionStats
                                                    └─> WebServer 快照（给前端轮询/推送）
```

三个实现细节值得记：

1. **不设 `SO_REUSEADDR`**。Windows 上该选项对 UDP 相当于 `SO_REUSEPORT`，会让第二个实例静默绑定同一端口，导致"界面显示未连接但自动换挡还在工作"这类诡异 bug。作者选择直接绑定失败并报错。
2. **解析失败返回 `None`**，不抛异常打断接收循环。
3. **`is_live` 用 2.5 秒超时**判断遥测是否在线——但注意，这只是给 UI 看的，**决策层并没有据此停止发指令**（见 §4.2 我要改的地方）。

### 1.4 第二个参考项目：`forza-horizon-6-tgt2-shifter` 对照

你提供的第二个项目是 Bun + TypeScript（不是 Python），5 个源文件 5,185 行，`autoshift.ts` 单文件 2,665 行。它和第一个项目解决同一个问题，但**技术路线几乎相反**，对照价值极高。

**它的输入方案（关键情报）**

`src/key_agent.ts` 里明确写着：

```
 * Injection methods:
 *  E) vJoy virtual joystick — DirectInput device, zero FFB interference (DEFAULT)
 *  C) SendInput atomic tap — down+up in single call
 *  A) SendInput with 60ms hold
 *  B) keybd_event with 60ms hold
 *  D) PostMessage to foreground window
```

- **vJoy 是默认方案**，键盘只是兜底；而且它准备了 **4 种不同的键盘注入方式**。
- 这等于用工程实践承认了一件事：**键盘注入在 Forza 里会漏**。一个方法不行换下一个，最后干脆默认走 vJoy。
- 它的 vJoy 映射是：`按钮 1 = 倒挡，按钮 2–11 = 1–10 挡，按钮 12 = 离合`，并提示"进游戏把每个挡位绑到对应按钮"。这说明 **Forza 的控制菜单确实能绑定 vJoy 按钮**（至少 FH6 可以）。
- 它用**常按**而不是脉冲：`vjoyHoldGear()` 始终保持"当前挡位那个按钮按着"，只在换挡时松开旧的、按下新的。这符合"Forza 的独立挡位按钮是状态型输入"的语义。

**它的换挡算法（另一条路）**

不用"峰值功率 + 偏移"，而是**轮上推力交叉点**：

```
当前挡推力 ∝ 功率(当前转速) × 当前挡齿比
目标挡推力 ∝ 功率(目标挡落点转速) × 目标挡齿比
当 目标挡推力 ≥ 当前挡推力 × (1 + 2%) 时升挡
```

物理上这更"正确"：它自动考虑了齿比疏密——密齿箱和宽齿箱的最优换挡点本来就不同。而且它把换挡成本也建模进去了（`shiftTimePenaltyMs: 400`，算"换挡亏掉的时间多久能赚回来"）。

它还有几个值得抄的细节：

| 细节 | 值 | 为什么重要 |
|---|---|---|
| 起跑宽限期 | 车速 < 10 km/h 不发指令 | 发车格上遥测档位不可靠，让游戏自己起步 |
| 最小持挡时间 | 1,200 ms | 防止连续换挡抖动 |
| 反向锁 | 2,500 ms | 刚升完不许马上降 |
| 换挡执行超时 | 2,000 ms | 比第一个项目的 700 ms 保守得多 |
| 转速落定等待 | 900 ms | 换挡后等转速与轮速对齐再继续决策 |
| 挡位 × 车速有效性 | `getMinSpeedForGearKmh()` | 防止升进"这个速度挂不住"的挡 |

**它的授权状态**：仓库里**没有 LICENSE 文件**。按著作权法默认"保留所有权利"，比 AGPL 更严格——不能复制、不能分发衍生作品。所以两个项目都不能抄代码。

**两个项目对照结论**

| 维度 | 第一个（fh6-virtual_tcu） | 第二个（tgt2-shifter） | 我们取谁 |
|---|---|---|---|
| 语言/生态 | Python + Electron | TypeScript + Bun | Python（你我都好维护） |
| 输入默认 | 键盘（vJoy 可选） | **vJoy（键盘兜底）** | 学第二个：vJoy 优先 |
| 换挡判据 | 峰值功率 + 置信度融合 | **轮上推力交叉** | 学第二个（物理更硬） |
| 学习机制 | 抛物线拟合 + 断油检测 | 转速分箱功率表 + 断油置信度 | 两者结合 |
| 防误换挡 | 待确认 + 软上限 + 退避 | 多重时间锁 + 落定等待 | 学第一个的退避，学第二个的时间锁 |
| 失败可见性 | 有 `_last_decision` 字段但基本没填 | 有 decision log，1 秒一条 | **我们自己做得更彻底** |

## 2. 核心算法说明

### 2.1 遥测解析（必须重写的部分）

`telemetry/parser.py` 全部是硬编码偏移，例如：

```python
speed, power, torque = struct.unpack_from("<fff", data, 256)
accel  = data[315]; brake = data[316]; clutch = data[317]; gear = data[319]
car_ord, car_cls, pi, drivetrain, ncyl = struct.unpack_from("<iiiii", data, 212)
```

这些偏移量对应的是 **Horizon 布局**（324 字节，Dash 区起点 244）。它只做了一件事：`if len(data) < 324: return None`。

> ⚠️ **致命细节**：FM8 的包是 331 字节，长度检查会**通过**。然后 `data[319]` 在 FM8 里读到的是"左后轮胎磨损量"这个 float 的第 1 个字节，得到 0–255 的随机值。程序不会崩，只会拿垃圾数据换挡。这就是为什么不能沿用它的解析代码——它连"报错"都不会给你。

它还做了一件对的事：`speed_kmh` 有个兜底——若 `speed` 字段不在 `[0, 200)` m/s 内，就用 `|Velocity|` 反算。FM 系列的 Speed 字段偶发异常，这个兜底要保留。

另一处要警惕的语义假设：

```python
is_shifting = gear > 10
```

在 FH6 里档位编码是 `0=R, 1–10=前进, 11=N`（见 `replay.py` 的 `_gear_label`），所以 `>10` 把 **N 挡也当成了"换挡中"**——这本身就可疑。FM8 的档位语义没有任何公开文档，必须实测（阶段 2 的第一项任务）。

### 2.2 基础升挡曲线：三点折线

最朴素也最稳的一层。油门 → 升挡转速占比，三个锚点线性插值：

```
油门 0.0 → 40%   油门 0.5 → 58%   油门 1.0 → 82%     （COMFORT 默认值）
```

对应 `TCULogic._curve()`。轻油门早升挡（省油、平顺），全油门晚升挡（用满功率）。这是所有模式的底座。

### 2.3 齿比学习（`GearRatioCalibrator`）

**目标**：知道"当前车速挂到目标挡位后转速会是多少"，用于防超转、防抖动。

**做法**：学习每挡的 `rpm / km/h` 比值。

- 采样条件：车速 > 25 km/h、转速 > 0、有正扭矩、非换挡中、轮滑 < 0.8（打滑会破坏轮速-转速关系）
- 比值合法区间：15 ~ 500（超出即丢弃）
- 收敛：`rate = max(0.08, 1/(n+1))`，早期是真平均，后期是低通滤波
- 异常剔除：偏离当前值 > 18% 直接丢（前 5 个样本豁免）
- **单调性校验**：高挡的比值必须小于低挡（容差 3%），否则拒绝。这能挡住"换挡瞬间抓到一帧"的脏数据

**预测**：`project_rpm_after_shift(td, target_gear) = ratio[target] × speed_kmh`

这个量是整个防抖体系的基石：降挡前先算"挂进去会不会超转"，升挡后算"落点会不会掉出功率带"。

### 2.4 功率曲线拟合（`PowerCurveDetector`）

**目标**：从"扭矩-转速"散点里推断峰值扭矩转速和峰值功率转速，而不需要跑马力机。

**做法**：增量最小二乘拟合二次曲线 `torque = a·r² + b·r + c`（`r` 是转速占比 0–1）。

- 只保留 8 个累加量（`n, Σx, Σx², Σx³, Σx⁴, Σy, Σxy, Σx²y`），O(1) 内存
- 每次采样把旧累加量乘 `0.9997` 衰减 → 车辆调校变了模型能慢慢跟上
- 解 3×3 行列式得 `(a,b,c)`
- 峰值扭矩：`r = -b/(2a)`（要求 `a < 0`，即开口向下）
- 峰值功率：功率 ∝ `torque × rpm` = `a·r³ + b·r² + c·r`，求导 `3a·r² + 2b·r + c = 0` 取根。若红线处导数仍 > 0（高转自然吸气机，如 S54），直接把峰值功率定在 0.97——"越晚换越好"

**置信度**（这是它最讲究的地方）：

```
conf = 样本数置信 × 分布宽度置信 × 高转覆盖置信
```

- 样本数：8 → 80 线性
- 分布宽度：样本的 `r` 标准差 0.035 → 0.085 线性。**注释里写明**：真实驾驶中 TCU 总把转速压在高段，分布天然很窄，早期版本要求 0.16 导致"永远学不会"
- 高转覆盖：最高采到的转速占比，0.40 → 0.90

三道闸门缺一不可，任一为 0 就整体为 0。因为"只有中段数据"拟合出的抛物线，峰值位置会严重偏低。

**输出**：`optimal_upshift_rpm = conf × (peak_power_rpm + offset) + (1-conf) × fallback`

即：数据不足时用配置值，数据充分时信模型，中间平滑过渡。**没有硬开关**（作者注释说，早期加过硬 gate，结果模型永远不生效）。

### 2.5 断油转速检测（`RevLimiterDetector`）

**为什么需要**：Forza 报的 `EngineMaxRpm` 是"名义红线"，很多车的实际断油点只有它的 84%–93%（作者实测 Ford GT 断在 88.3%）。按名义红线换挡 = 一直撞断油 = 白损失加速。

**识别签名**：全油门（> 0.92）下，转速**不再上升**且**在固定高度来回锯齿振荡**。

- 滑动窗口 24 帧，要求窗口内 `max-min > 150 rpm`（有振荡）
- 统计上升沿 ≥ 2 次、下降沿 ≥ 2 次（排除单次冲击/换挡抖动）
- 峰值锚点：`wmax` 连续 18 帧不明显上移（> 40 rpm 视为仍在爬升）
- 上限保护：不超过名义红线的 100%；下限保护：不低于名义红线的 78%

**最难的一关**：`_max_wot_rpm` 下限。若某次误判把断油点定在 9,765 rpm，而发动机明明跑到过 11,524 rpm，那这个值一定是错的（`MAX_SEEN_TOLERANCE = 0.99`）。作者用"发动机实际跑过的最高转速"作为硬地板，并在加载旧档案时用功率曲线记录的历史最高转速重新校验一次。

**跨挡确认**：一次换挡会清空窗口，导致单挡内攒不满 18 帧。所以把多个"独立候选事件"（不同挡位/不同加速段）的峰值存起来，2 次在 1.5% 内一致就升级为"已验证"。

### 2.6 高挡"速度墙"与挡位停滞

赛道车的高挡常常"到不了目标转速"：空气阻力把加速度压到接近 0，转速以 0.5%/秒爬升，永远到不了 94%。

- **平台检测**（`_observe_high_gear_load_plateau`）：1.4 秒窗口内，转速峰谷差 ≤ 2.5%、转速增长率 ≤ 0.5%/s、速度增长率 ≤ 1.0 km/h/s → 判定"这一挡卡住了"
  - 证据分级：峰值 ≥ 86% 只需一个窗口；低于 86% 必须额外保持 1.5 秒（防止把"高挡正常加速"误判成"到顶了"）
- **停滞检测**（`_observe_gear_stall`）：3.0 秒窗口、转速变化 ≤ 2%、且已过峰值功率点、按当前速率估算"到达目标还要 > 6 秒" → 判定"这挡没戏了"

两个检测的产物都只能把升挡点**往下压**，且压在"实测峰值"和"峰值功率转速"之上，绝不允许压到模式的中段阈值以下。

### 2.7 防误换挡体系（最有价值的部分）

这是从 issue #1 一路修到 #74、PR 到 #76 反复打磨出来的，逐条列：

| 机制 | 作用 | 参数 |
|---|---|---|
| 全局换挡冷却 | 一次换挡后短时间内不再换 | 350 ms |
| 分状态级联冷却 | 不同原因的降挡冷却不同 | 刹车/失配 0.3s、kickdown 0.7s、滑行 0.6s、其他 0.9s |
| 升挡待确认（pending） | 发出升挡后等游戏真的换挡 | 超时 0.7s |
| 软上限 + 指数退避 | 超时未确认**不判定为"已到最高挡"**，而是暂时封顶并退避重试 | 0.8s × 2ⁿ，上限 8s |
| 换挡中不算确认 | `gear > 10` 期间延长等待，而不是当作成功 | +0.35s |
| 手动干预识别 | 档位变了但 `_we_shifted == False` → 说明用户自己换的，加锁 | 升 0.5s / 降 0.8s |
| 防抖动（anti-hunt） | 降挡前算目标挡落点转速，若已接近升挡阈值就不降 | 阈值 − 0.08 缓冲 |
| 超转保护 | 目标挡投影转速 > 红线 × 1.02 → 拒绝降挡 | 1.02 |
| 腾空/失重 | `accel_y < -6` 持续 3 帧 → 冻结所有决策 | 落地后 0.9s 恢复 |
| 横摆瞬态 | 短暂横摆尖峰（≤400ms）= 救车，冻结决策 | 结束后再保持 200ms |
| 碰撞识别 | 单帧速度骤降 > 25 km/h | 立即解除换挡锁 |
| 静止/倒挡/防熄火 | 低速强制降挡、倒挡期间 TCU 完全被动 | 1100 rpm |

**特别值得学的一条**：`_shift_down` 里那句

```python
projected = self._calibrator.project_rpm_after_shift(td, td.gear - 1)
if projected is None:
    projected = td.current_rpm * (td.gear / max(td.gear - 1, 1))
```

没有齿比数据时用"按档位比例粗估"兜底——宁可估得糙，也不要在没有保护的情况下降挡。

### 2.8 驾驶模式设计

五种模式，本质是**同一组规则的不同参数 + 不同优先级**：

| 模式 | 定位 | 升挡点 | 特点 |
|---|---|---|---|
| COMFORT | 巡航 | 40/58/82（油门三点） | 刹车降挡保守、有巡航省油升挡、滑行降挡 |
| RACE | 赛道 | 80/94（中/满油门） | 刹车降挡激进、动力降挡（corner exit）、下坡发动机制动、着地恢复 |
| DRIFT | 漂移 | 92 升 / 65 降 | 只守功率带，不参与其他逻辑 |
| OFFROAD | 越野 | 72/90 | 扭矩优先、允许打滑升挡、爬坡降挡 |
| MANUAL | 手动 | — | TCU 完全不发指令，只给"建议升/降"提示 |

COMFORT 还会叠加一层 `DriveStyleTracker`：一个 0→1 的"运动指数"，油门/刹车/横向 G/转速加权，上升时间常数 0.3 秒、下降 6 秒（"一脚地板油立刻变运动，松油门要很久才回落"）。指数 > 0.30 进入 ADAPTIVE，> 0.55 进入 SPORT，带 0.03 迟滞防抖。进入 SPORT 后升挡曲线整体换成 dynamic 版。

**这个设计的优点**：参数集中、模式可解释。
**缺点**：5 个模式 × 每条规则的组合，测试面爆炸——23 个测试文件里有一半是在修特定模式下的特定 bug（issue #67 低挡抖动、#74 升挡过晚……）。

### 2.9 输入模拟实现

**键盘后端**（`keyboard_output.py`）

- 单线程 `ThreadPoolExecutor(max_workers=1)` 串行化按键，避免多线程交错
- `keyboard.press(key)` → 保持 `KEY_HOLD_S = 40ms` → `keyboard.release(key)`
- **self-press 窗口**：注入后 150ms 内，把同一个键标记为"自己按的"，防止" paddle 监听器把注入的按键误认为玩家手动操作"
- 离合序列：按下离合 → 等 20ms → 按换挡键 → 保持 55ms → 松换挡 → 等 25ms → 松离合
- 注意点：它对 `except` 的处理是"尽力释放"（`finally` 里补 release），防止卡键

**vJoy 后端**（`vjoy_output.py`）

- 用自带 `pyvjoy`（ctypes 直连 `vJoyInterface.dll`），`VJoyDevice(1)`
- 两种模式：
  - `direct_shift = True`：直接按 `B1..B10` 对应挡位（需要游戏里把 1–10 挡绑到这些按钮）
  - `direct_shift = False`：退回顺序换挡，点 `B13`（升）/ `B14`（降）
- 按键保持 `BUTTON_HOLD_S = 60ms`——注释写得很明白：**要跨过游戏多个输入轮询帧，零长度脉冲会漏**
- 直选模式下**不释放按钮**（`reset_buttons()` 后才重设），因为直选挡位是"状态型"而非"脉冲型"
- 同样单线程 executor 串行化

**一条重要的历史教训**（README 和 commit 记录都写了）：项目曾支持"虚拟 XInput 手柄"输出，后来**删除**了。原因：作为第二个 XInput 设备，每次换挡都要发整包手柄状态，把玩家的转向/油门打回中位，导致转弯时车"发卡"。这直接决定了我们的技术选型——**不做虚拟 XInput 手柄**。

### 4.3 可以复用（重新实现）的算法

按价值排序：

1. **齿比学习 + 换挡后转速预测** — 防超转、防抖动的地基。直接照搬设计，参数需重调
2. **断油转速检测（含"实测最高转速"地板）** — 对 FM8 同样成立，甚至更重要（FM8 车辆改装后名义红线和实际断油差得更多）
3. **功率曲线二次拟合 + 三因子置信度** — 决定"什么时候该换"的核心
4. **`pending` 换挡确认 + 软上限 + 指数退避** — 防连发、防卡死的关键
5. **anti-hunt（降挡落点检查）** — 消除"降了立刻升"的抖动
6. **高挡平台 / 挡位停滞检测** — 赛道车必备
7. **模式 = 规则优先级表 + 参数集** 的组织方式
8. **三点油门曲线** 作为无学习数据时的兜底
9. **二进制录制 + 回放回归测试** — 这是它能在不断改算法的情况下不把老问题改回来的原因
10. **车辆指纹 `(ordinal, class, PI, tune_signature)`** — 区分同款车的不同调校

### 4.4 输入方案决策

**修订依据**：`tgt2-shifter` 默认使用 vJoy，并为键盘写了 4 种注入方式——说明键盘注入在 Forza 系里确实不稳定；同时它证明 Forza 的控制菜单能绑定 vJoy 按钮。你用的是 Xbox 手柄，这改变了风险排序。

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| **vJoy（DirectInput 虚拟设备）** | 不干扰手柄/方向盘的模拟量；按钮是"离散事件"，不会漏；可直选挡位 | ① Forza 对设备枚举顺序敏感，可能只认"设备 1"；② 与真实手柄/方向盘同插时可能被抢（社区解法是 Hush 隐藏真实设备）；③ vJoy 原版停维护，需用 BrunnerInnovation 的 fork；④ **FM8 能否绑 vJoy 按钮仍未经实测** | **主线方案（阶段 3 先 spike）** |
| **键盘注入（SendInput 扫描码）** | 零驱动、必定能跑起来；不碰模拟量 | ① **实测会漏**（两个项目都为此写了多种注入方式）；② 小键盘键受 NumLock 影响；③ 游戏若用 Raw Input 可能收不到 | **保底方案，必须实现且可切换** |
| ~~虚拟 XInput 手柄~~ | — | 参考项目实测：整包状态会覆盖玩家转向/油门 | **明确排除** |

**为什么"手柄用户"反而更适合 vJoy**：手柄玩家本来不用键盘开车，插一个虚拟设备不占手指；而且 vJoy 的按钮是离散事件，不像键盘长按会触发系统按键重复。代价是 Forza 可能把"最后接入的设备"当主控制器——必须实测。

**阶段 3 的决策实验**（半天可完成）：

1. 装 vJoy，配置 Device 1：至少 8 轴 + 14 按钮（我们的映射：`B1..B10` = 1–10 挡，`B11` = 倒挡，`B12` = 离合，`B13/B14` = 顺序升/降）
2. 打开 FM8 → 设置 → 控制，看该设备是否出现、能否绑定
3. 用探测工具逐个按钮扫掠，观察游戏是否响应
4. **同时插入 Xbox 手柄**，看两者是否互相干扰
5. 结果记入 `docs/03-decisions.md`

**判定标准（全部满足才进阶段 4）**：
- 连续 20 次升挡 + 20 次降挡，游戏内 100% 生效
- 同时插手柄时仍 100% 生效
- 测出"发指令 → 遥测档位变化"的中位延迟（预期 80–200 ms）

任意一条不满足，就退到键盘方案，把 vJoy 降级为"实验性可选项"。

### 4.5 安全设计（比参考项目更严格）

参考项目的软肋：**遥测断了，决策层并不会主动停手**——`is_live` 只用于 UI 显示。我们要补上：

| 机制 | 实现 |
|---|---|
| 遥测新鲜度看门狗 | 独立 10 Hz 守护线程。>300 ms 无包 → 暂停发指令；>2 s → 状态转为 DISCONNECTED，清空所有 pending |
| 启用/停止双开关 | 热键（默认 F11）+ GUI 开关 + 启动默认**关闭**（fail-safe） |
| 全局急停 | F12：置位 kill flag → 输出层每次发送前检查 → 释放所有按住的键/按钮 |
| 发送前五重校验 | `is_race_on == 1`、`rpm > 0`、`gear` 在合法区间、`speed` 有限、距上次换挡 > 冷却 |
| 限速 | 任何 1 秒窗口内最多 4 次换挡；同向指令最小间隔 350 ms |
| 回读校验 | 发指令后 700 ms 内档位未变 → 记失败，指数退避（0.8s → 8s 封顶） |
| 退出清理 | `finally` 中释放 vJoy 全部按钮 + 释放键盘按键 + 保存档案 |
| 遥测异常保护 | 单帧 `NaN/Inf`、`rpm > maxrpm×1.1`、`|v| > 150 m/s` → 丢弃该帧并计数，连续 30 帧异常 → 停用 |

### 4.6 我们要改进的地方（不是照搬）

| 参考项目的做法 | 我们的做法 | 原因 |
|---|---|---|
| 接收线程里跑完整决策 | 接收线程只更新不可变快照；决策在独立线程按固定 60 Hz 步长跑 | 网络抖动不会拖慢决策；决策耗时不影响收包；便于注入测试时钟 |
| 单文件 2,296 行 | 每条规则一个类，模式 = 规则优先级表 | 可单测、可组合、加规则不改老代码 |
| 规则里硬编码数字 | 全部进 `Config` dataclass，带范围校验 | 调参不用改代码 |
| 直接访问 `_calibrator._ratios` | 定义公共只读 API | 降低耦合 |
| 5 种模式 | 首版 3 种（SPORT / RACE / MANUAL） | 减少测试面，先把一条链路做扎实 |
| UI 用 Electron + Vue | Python 原生 GUI | 对非程序员维护成本低得多 |

### 4.7 已知故障诊断：为什么"时不时换不上挡"

你遇到的现象，在这两个项目的代码里都能找到直接对应。按可能性排序：

| # | 原因 | 代码证据 | 现象 | 我们怎么防 |
|---|---|---|---|---|
| 1 | **键盘注入被游戏漏掉** | 项目二为此写了 4 种注入方式并默认改用 vJoy | 偶发一次没反应，下一次又好了 | vJoy 优先；键盘方案发完指令后 700 ms 内校验档位，未变则只重试一次 |
| 2 | **变速箱不是"手动"** | 无（游戏设置问题） | 游戏自己换挡，TCU 的指令被覆盖；TCU 看到档位"自己变了"，判为玩家手动干预并加锁 → 一段时间完全不换挡 | 首次向导强制检查；检测到"档位变化但不是我发的"连续多次 → 提示"请把变速箱设为手动" |
| 3 | **"手动 + 离合"但没按离合** | 项目一有离合辅助开关，默认关 | 换挡指令被吞，档位不变 → 触发退避 | 文档明确；提供离合辅助开关；用实测延迟反推是否生效 |
| 4 | **升挡待确认超时 → 软上限 + 指数退避** | `_upshift_cap_by_key` + `_upshift_retry_backoff_s()`（0.8s → 8s） | 卡在某个挡位几秒不动，然后突然恢复 | 保留退避但上限压到 2 s；且**每次抑制都在日志里写明原因和剩余时间** |
| 5 | **`gear > 10` 被当成"换挡中"** | `parser.py: is_shifting = gear > 10`，而 Horizon 的空挡就是 11 | 一旦进过空挡，程序永久认为在换挡，完全不动作 | 不用这个判据；阶段 2 实测 FM8 的档位语义后，用"档位稳定帧数 + 待确认"重新定义 |
| 6 | **权限/焦点** | 无 | 游戏以管理员运行而工具不是 → Windows 的 UIPI 会拦掉注入，一次都发不进去 | 启动时检测是否同权限；提示"以管理员身份运行" |
| 7 | **保护规则误触发** | 低速/防熄火/碰撞/横摆锁 | 碰撞后或低速弯里"不换挡" | 每条规则都能在日志里看到"被谁挡住" |
| 8 | **时间锁过保守** | 项目二 `minGearHoldMs: 1200` + `reversalLockMs: 2500` | 主观"不跟手"，尤其连续弯 | 参数可调；默认取中间值（持挡 600 ms、反向锁 1.2 s） |

**我们要建立的一条铁律**：

> 任何一帧"没有换挡"，都必须能回答"为什么没换"。

参考项目定义了 `_last_decision = {"rule", "reason", "blocked_by"}` 这个结构，但整个 `tcu.py` 里几乎没往里写过东西——这是它最难维护的地方。我们的决策引擎每一帧都产出一个 `Decision`，包含：命中的规则、被哪条 guard 拦下、拦下的具体数值。GUI 上直接显示"当前为什么不动"，日志里也落盘。

这一条同时解决了"排障"和"教学"两件事：你能亲眼看到程序在想什么。

### 4.8 关于线上使用的说明

你的判断有依据：这两个项目都是纯外部遥测 + 输入模拟，不改游戏文件、不读内存，属于"外置助力"而非"作弊软件"。我不再把它当作主要风险来设计。

但仍保留两条工程约束，原因不是合规，而是可靠性：

1. **遥测断流必须停手**——线上网络抖动、观战/回放、菜单切换都会让数据不可信，盲目发指令会真的把车开坏。
2. **程序不隐藏自己**——不做反检测、不注入进程。出问题时你能一眼看出是它在动作。

### 阶段 2：独立遥测探针（只读，绝不发指令）

**目标**：证明"我们读到的 FM8 数据是准的、是实时的"。

**交付**：
- `tools/probe.py`：单文件、零第三方依赖（仅标准库）
- 自动识别包长（232 / 311 / 324 / 331）并明确提示是否为 FM8 Dash
- 实时面板：9 个必需字段 + 派生量（转速占比、油门%、车速 km/h、功率 kW）
- 统计：包率（1 秒窗口）、间隔中位数/P99、时间戳乱序次数、解析失败次数
- 自检告警：`|Speed − |v|| > 1 m/s`、`rpm > maxrpm×1.05`、`gear ∉ [0,12]`、`Accel/Brake > 255`
- 原始 hexdump（前 64 字节）+ 指定偏移的原始字节查看（用于反证偏移表）
- 录制为 `.bin.gz`；`--replay` 按 60 Hz 回放

**验收标准**：
1. 包率 60 ± 5 pps，10 分钟内解析失败 0 次
2. 手动 1→2→3→4 换挡，面板档位**逐挡同步**变化（这是偏移表正确性的最强证据）
3. 静止时 `Speed ≈ 0`、`Gear = 1`、`Accel = 0`；全油门 `Accel ≈ 255`
4. `Power`、`Torque` 与实际驾驶直觉一致（全油门低转扭矩大、高转功率大）
5. 关掉游戏 Data Out，探针在 2 秒内显示"离线"
6. 录制文件回放，字段序列与实时完全一致

**本阶段要回答的关键问题**（目前无公开答案，必须实测）：
- FM8 的 `Gear` 在 N 挡、倒挡、换挡过程中分别是什么值？会不会 > 10？

## 9. 你需要学什么（每次 20 分钟，按阶段给）

阶段 2 之前，只需要理解 **3 个概念**：

1. **字节偏移（byte offset）**
   把一个 UDP 包想成一条 331 个格子的纸条，每格 1 字节。`Gear` 是第 308 个格子（从 0 数起就是 307）。所谓"解析"，就是"按图纸去指定格子取值，再按类型翻译"。为什么容易错？因为格子号数错一位，读到的就是隔壁字段的一半——数字看着像真的，其实是垃圾。

2. **包率 / 采样率**
   游戏每秒发 60 个包，也就是每 16.7 ms 一个。你踩下油门到程序"看到"它，最多延迟 16.7 ms。这也是为什么换挡决策不能做得比 16.7 ms 更细——没有新数据，想再快也没用。

3. **状态机**
   "当前处于什么状态，就只允许做什么动作"。比如"换挡中"状态不允许再发换挡指令；"遥测断开"状态不允许发任何指令。程序的可靠性，八成来自状态机设计得对不对。

阶段 4 之前，再补 2 个：

4. **滑动窗口 / 移动平均**
   "最近 24 帧的转速最大值"这种说法。用来抗噪：单帧异常不影响判断，但持续的趋势能被抓住。

5. **滞回（hysteresis）**
   "升到 82% 才升挡，但要掉到 74% 才降挡"——中间留一条缓冲带，防止在阈值附近反复横跳。这是所有"防抖动"的通用手法。

**不需要学**：最小二乘拟合的推导、Web 前端、Electron、打包脚本的内部原理。这些我会处理，你只需要能看懂"它在干什么、为什么这么干"。

| 事项 | 决定 | 影响 |
|---|---|---|
| **许可证路线** | **独立实现**，不复制任何一份代码 | 你的项目可以自由授权；也避免把两个项目的 bug 一起继承过来 |

| **使用场景** | 先做能用的简单版本，线上问题暂不考虑 | 不做反检测；但仍保留"遥测断流即停手"这条可靠性约束 |

### 微软商店版的一个具体风险

Store 版应用可能运行在 AppContainer 沙箱里，默认禁止向 `127.0.0.1` 发 UDP。资料互相矛盾：

- 一份较严谨的项目文档称 **FM8 不使用 AppContainer，所有版本都不需要回环豁免**
- 一份模拟器厂商文档称 FM8（Store 版）**需要** `CheckNetIsolation.exe LoopbackExempt -a -n=...`

**处理办法（三层，从便宜到麻烦）**：

1. 先试 `127.0.0.1:5300` —— 大概率直接可用（官方文档明确写了 2023 版新增支持 localhost）
2. 不行就把游戏里的 Data Out IP 改成**你电脑的局域网 IP**（如 `192.168.1.x`），探针监听 `0.0.0.0` 照样能收到。这条路走的是真实网卡，完全绕开沙箱回环限制，只需放行防火墙
3. 还不行才动回环豁免

阶段 2 的探针在收不到数据时会直接把这三步打在屏幕上。
